The **Production Readiness Profile v2** turns Protoform's support claims into a versioned,
machine-readable capability ledger. It covers form-relevant Protobuf features, every current
Protovalidate rule family, CEL behavior, form-relevant Google AIP guidance, and production runtime
quality.

The catalog is grounded in the current [Protobuf language guides](https://protobuf.dev/programming-guides/),
[Protovalidate standard rules](https://buf.build/docs/reference/protovalidate/rules/),
[CEL language overview](https://cel.dev/overview/cel-overview), and
[general AIP catalog](https://google.aip.dev/general). The profile narrows those broad specifications
to behavior a TypeScript form library can own and shows excluded responsibilities explicitly.

The current Profile v2 score is **100%: 174 of 174 applicable checks verified**. Another 16 excluded
checks stay visible without affecting the percentage: 13 external, 1 verified optional, 1 out of
target, and 1 superseded. Protoform is therefore **production ready** by the profile's strict
definition. The maintained Protobuf-ES v1 bridge is verified optional migration support, but it
remains outside that claim; the canonical runtime target is Protobuf-ES v2.

## What the percentage means

The overall percentage is `verified / applicable`:

- **Verified** requires automated evidence: a test file and test name that exist in this repository.
- **Gap** is applicable behavior promised now but missing sufficient automated evidence.
- **Deferred** is applicable behavior intentionally scheduled after this release. It counts against readiness and names the next test.
- **Unsupported** is applicable upstream behavior that Protoform does not currently handle. It counts against readiness and names the next test.
- **Optional** is an evidence-backed add-on or migration capability excluded from the canonical denominator.
- **Out of target** is current upstream behavior Protoform explicitly does not promise in this profile.
- **External** is owned by a backend, transport runtime, or governance process and is excluded from the denominator.
- **Superseded** was removed or replaced upstream and is excluded from the denominator.
- The **required profile** highlights the non-negotiable subset.

`Production ready: yes` requires every applicable check to be verified and the referenced test
suites to pass. Documentation, implementation code, or a manual claim alone cannot increase the score.
The evidence-integrity test also fails if a verified row points to a missing test.

The release gate is narrower than the production-readiness claim. It passes when there are no
unplanned `missing` rows and every verified evidence reference remains valid. Approved deferred and
unsupported rows remain visible and reduce readiness, but do not make every current build fail. A
passing release gate must not be read as `Production ready: yes`.

This prevents a broad claim such as "supports Protobuf" from hiding untested scalar families, presence
semantics, well-known types, validation operators, or error-path behavior.

## Run the report

```bash
bun run readiness:report
```

Get the complete profile as JSON for another dashboard or CI artifact:

```bash
bun run readiness:report -- --json
```

Run the same release gate used by CI:

```bash
bun run readiness:gate
```

CI runs `readiness:gate` after the conformance suite. It exits non-zero when an unplanned gap enters
the profile. The evidence-integrity test separately rejects missing evidence files or test names.

Run the same AIP-180 compatibility check against the target branch:

```bash
bun run proto:breaking -- --against '.git#ref=origin/main'
```

The check uses Buf's `FILE` policy for the stable protobuf modules. Exact allowlist entries preserve
the previously approved pre-1.0 file moves and enum removal; no rule category is disabled, and every
other compatibility violation fails. CI compares pull requests with their base commit and main
pushes with the previous commit. The isolated expected-failure fixture proves a field type change is
rejected.

Verify the public source-copy distribution locally:

```bash
bun run registry:build
bun run registry:consumer-smoke
```

That serves the built registry, installs the bookstore plus both form engines into a clean consumer,
and type-checks only the copied source and public third-party dependencies.

## Scope of Profile v2

The denominator is explicit rather than pretending every Protobuf or AIP feature belongs in a form library:

| Area | Verified | Applicable open work | Excluded |
| --- | --- | --- | --- |
| Protobuf | Canonical v2 behavior, Editions 2023 descriptors, unknown-field preservation, and service/RPC workflow classification | None | The maintained Protobuf-ES v1 bridge is verified optional; extension and deprecated group discovery are out of target; binary codec compatibility remains Protobuf-ES-owned |
| Protovalidate | Required/ignore behavior and every current scalar, collection, well-known-type, example, and predefined-rule family | None | Removed `disabled`/`skip` options are superseded by current ignore semantics |
| CEL | Field/message results, nested paths, multiple violations, partial unknowns, cost limits, failures, and UI expressions | None | Backend authorization and policy enforcement remain server-owned |
| AIP | Resource metadata, standard request shapes, transcoding roles, method classification, long-running operations, job/import/export workflows, quantity and standardized-code fields, ranges, partial results, retries, policy preview, masks, etags, structured errors, and compatibility enforcement | None | AIP governance, launch review, authorization enforcement, and repository ownership |
| Production runtime | Form-framework integrations, generated forms, steppers, accessibility, resilience, browsers, compatibility, security, and performance | None | None |

Runtime evidence includes axe checks across representative form states, keyboard-only step recovery,
Chromium/Firefox/WebKit configuration, narrow-viewport overflow checks, hydration checks for every
docs example, abortable validation and submission, 50/200/500-field budgets, bundle and tree-shaking
budgets, registry-only consumer installation, and malformed-input/HTML-injection cases.

The profile is deliberately granular. A table-driven test may verify many values inside one capability,
but a single broad integration test cannot mark unrelated feature families as complete.

## How to maintain 100%

Profile v2 counts client-owned deferred and unsupported work instead of hiding it behind a broad
not-applicable label. Future work should deepen evidence without weakening the denominator:

- **Evidence depth, not a boolean.** Require the relevant combination of unit, conformance, browser,
  and isolated-consumer evidence for each capability. Record the upstream specification version and
  evidence freshness instead of allowing one test reference to carry every confidence level.
- **Consumer deployment matrix.** Install the packages and registry output into fresh Vite and
  server-rendered React applications, then verify production builds, hydration, client boundaries,
  and supported React and framework versions.
- **Schema evolution and drafts.** Extend the new top-level unknown-field preservation through nested
  edits, then cover renamed, moved, and removed fields, unknown enum values, version skew, and staged
  v1-bridge upgrades without silent data loss.
- **Security and misuse resistance.** Add property and fuzz tests for malformed descriptors, deeply
  nested input, oversized collections, CEL budget exhaustion, secret leakage, and package provenance.
- **Network lifecycle and operability.** Extend the verified retry and long-running-operation core
  through offline recovery, reconnect storms, cross-tab cancellation, and redacted telemetry hooks.
- **Human accessibility verification.** Track screen-reader checks, 400% zoom, forced colors, reduced
  motion, and touch targets separately. Manual evidence stays visible but does not inflate the
  automated readiness percentage.
- **Advanced form UX.** Exercise remote option loading, localized values and messages, draft autosave,
  large repeated-field virtualization, and cross-step asynchronous dependencies.

## Adding or closing a check

1. Add the smallest failing conformance or runtime test for the capability.
2. Implement the behavior and make the focused test pass.
3. Change the matching row in `readiness/profile.ts` from `missing`, `deferred`, or `unsupported` to `verified` and point it to that test.
4. Run `bun run test:conformance`, the owning test suite, and `bun run readiness:report`.
5. Review the denominator when an upstream specification adds a new form-relevant feature.

Profile changes should be reviewed like public compatibility changes: the capability ID stays stable,
new requirements are added explicitly, and removals require a documented scope decision.
